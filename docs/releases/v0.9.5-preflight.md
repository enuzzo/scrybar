## Publication mechanism and source scope

`.github/workflows/build-firmware.yml` runs for `v*` tags and manual dispatch.
It builds Astro, builds firmware with public empty Wi-Fi configuration and DOOM
disabled, uploads the four firmware files as an Actions artifact, then deploys
Pages after the firmware and Swift test jobs pass. It does **not** create a
GitHub Release or a Companion DMG. The Pages environment permits `main` branches
and `v*` tags. Manual dispatch on main also deploys; it is not a dry run.

CI has been aligned to the installed firmware toolchain: ESP32 core 3.3.6,
LVGL 8.3.11, ArduinoJson 7.4.2, GFX Library for Arduino 1.6.4, pngle 1.1.0 and
SensorLib 0.3.1. The board options retain 240 MHz CPU, hardware USB CDC, QIO,
16 MB flash, custom partitions and OPI PSRAM.

The local development main is 29 commits ahead of public main, plus current
uncommitted work. Those commits are ScryBar work, but their ancestry includes
old DMGs, icon proposals and optional Studio TV development. Publication should
use the coordinator's selected snapshot based on public main, rather than push
all that local history or stage every untracked file.

Exclude private backups/configuration, raw `output/` and screenshots, generated
build/cache trees, local app/DMG archives, obsolete tracked DMGs, icon proposals
and the personal INFO capture. `secrets.h` is ignored and not tracked. The
original DOOM WAD is tracked in the old public tree despite its ignore rule;
exclude it from the new source tree/archive. The public build uses a 12-byte
stub and `-DDOOM_SPIKE_ENABLED=0`. No history rewrite is required for this release.

The older `docs/flasher/manifest-{full,lite}.json` files are legacy manifests;
the active Pages workflow publishes `web/public/manifest.json` as `/manifest.json`.
Its installation parts are bootloader at 0, partitions at 32768, boot_app0 at
57344 and application at 65536. Manifest version and visible site version are
both supplied from the release tag during CI.

Only the necessary public asset headers and assembly are added. Its sole
credentials input is `.github/ci-secrets.h`: all ten Wi-Fi defines are empty.
The local private `secrets.h` is never opened or copied.

The build requests `--clean --jobs 2` using Arduino CLI 1.5.1. The requested

## Concrete release order

1. Finish and verify Companion 0.3.15 (53), including the ScryBar/Meguru artwork
   recovery regression. Build a universal Release DMG outside Dropbox; verify
   its mounted app, executable parity, signature, architectures and checksum.
   Preserve the previous package in the local ZIP archive before replacing it.
2. Finalize one curated public source commit based on the current remote main.
   Include the approved firmware, Companion, website, tests, source manifests
   and sanitized evidence. Complete all versioned download links and notes.
3. Publish the immutable `companion-v0.3.15` preview with DMG, Companion-only
   source ZIP, `SHA256SUMS.txt` and `SOURCE_SHA256SUMS.txt`. Keep its preview/ad-hoc
   status explicit; do not replace existing release assets.
4. Make the curated commit the public main via a fast-forward update, or change
   new source/document links to point at the release tag. The site currently
   uses main links for its new reports; tag-only publication without updating
   those links would leave them unavailable.
5. Push `v0.9.5` at that exact curated commit to trigger the firmware/site
   workflow. Wait for firmware, Swift and Pages success. Retrieve the CI
   `scrybar-firmware` artifact and attach its exact bytes to the v0.9.5 release,
   with installation instructions and SHA-256 sums. The workflow does not do
   this Release-asset step automatically.
6. Re-read the public manifest and website, verify version/download links, and
   download all four live firmware parts and release assets again. Their hashes
   must match the recorded CI/package artifacts. Verify source-archive contents
   against the published source manifest before claiming completion.

Authorization to publish does not substitute for the outstanding package,
artwork, CI and public-download checks. Physical acceptance and publication
results belong in the final release record once completed.
